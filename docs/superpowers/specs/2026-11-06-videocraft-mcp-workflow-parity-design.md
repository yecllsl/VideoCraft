# VideoCraft MCP 剪辑工作流能力对照设计

## 意图

避免剪辑工作流在开发和测试环境间出现直到用户操作时才暴露的工具缺口。以 NAS 远程剪辑工作流为目标，对照开发 stdio MCP、测试 HTTP MCP、共享 core、配置和验收测试；把差异分类并提前处理，再按开发验证、测试部署、测试环境验收的顺序交付。

## 目标

- 建立剪辑工作流能力矩阵，覆盖素材自检/盘点/预览、ASR 转写、确认文案字幕对齐、分镜合成、任务状态/取消、输出验收与记录。
- 对每项标记为“远程必需”“有意不远程暴露”或“工作流外”，说明接口、环境、验证状态和缺口。
- 为远程 MCP 增加受约束的 ASR 候选转写能力，复用 `videocraft_core.tasks.caption` 与项目 faster-whisper 实现，不另造识别算法。
- 转写输入仅接受 raw 逻辑 URI，候选稿写入配置 namespace 下的 projects；禁止 raw/output 写入、任意物理路径、覆盖既有文件和返回服务端物理路径。
- 扩展自动化合同/集成验收，使工具名、参数 schema、capability 报告、URI 边界、模型依赖、超时/错误行为和实际转写可检测；部署后验证运行中的测试 HTTP MCP 与 NAS，而非仅检查代码。
- 将已知但不属于远程剪辑服务的能力差异（TTS、通用编码、NLE 导出、脚本转分镜等）明确记录为有意不暴露，不为追求工具数量一致而开放。

## 非目标

- 不将开发 stdio MCP 的所有本地工具复制或暴露到测试 HTTP MCP。
- 不自动提交合成，不绕过 mapping 的用户确认闸门，不把 ASR 输出视为确认文案。
- 不在本任务实现新 ASR 模型、纠错模型或转写编辑器。
- 不改变原始媒体、现有成片或其他项目；部署只针对服务端测试 checkout 和服务。
- 不修改客户端认证方式或引入服务端开发环境常驻服务。

## 方案比较

1. **只增加远程转写工具**：最快，但容易留下 capability 报告、工具契约、超时/模型部署以及其他工作流工具差异未被检查的问题。
2. **剪辑工作流能力矩阵 + 定向补齐（推荐）**：先审计本工作流用到的所有能力，明确远程必需与有意排除项；实现缺口并增加合同及部署后验收。工作量适中，可在未来改动时用矩阵避免重复发现。
3. **开发与远程工具完全同构**：看似容易理解，但会扩大 NAS 服务权限面，把本地 TTS、任意路径编码、NLE 文件导出等不适合远程服务的能力开放出来，且与现有 URI/worker 安全边界冲突。

选择方案 2；范围已由用户确认。

## 当前事实与约束

- 服务端开发和测试 checkout 当前基线 `0f3b440`，目录分别为 `/root/projects/videocraft/`、`/opt/videocraft/`；开发 checkout 有用户未提交改动，实施必须先逐项检查并保留。
- 开发 stdio MCP `mcp/videocraft_mcp/__init__.py` 注册本地路径接口，包括 `caption_srt`、`strict_subtitles`、`probe_media`、`extract_frames`、`assemble_storyboard` 等；`pyproject.toml` 声明 faster-whisper，`videocraft_core.tasks.caption` 输出本地 SRT 和统计。
- 测试 HTTP MCP 是独立且刻意收敛的远程接口；现有 9 个远程工具包括 selfcheck、probe、frames、list_directory、storage_probe、strict_subtitles、assemble、status、cancel。共享存储访问必须走 `StorageResolver` 和逻辑 `nas://` URI。
- 工作流项目规范：`raw` 只读；字幕/候选稿写入 `projects/<namespace>/<project>/`；成片只写 output；不覆盖；ASR 仅候选，最终文案须对照原音人工校订；未确认 mapping 不得生成最终字幕或提交合成。
- 测试服务器常驻服务的部署目录是 `/opt/videocraft/`。先在开发环境验证，再有控制地更新测试环境并验收。不得混淆或在本任务中改动测试以外的环境。
- 开发环境已存在未提交变更，至少涉及 `mcp/videocraft_mcp/tools.py`、`videocraft_core/acceptance.py` 和多个测试文件；需区分既有用户修改与本次改动，不能覆盖或清理。

## 能力矩阵范围

矩阵覆盖工作流阶段：环境/工具能力自检、raw 项目目录和 output 基线、媒体元数据与帧预览、候选 ASR 转写、用户确认文案的严格字幕对齐、storyboard 合成、异步任务查询/取消、成片媒体/字幕验收、客户端记录。

有意不远程暴露：TTS、通用编码、任意文件路径版本的 caption/strictsubs、NLE 工程导出、脚本转分镜等开发机本地或高权限工具。逐项检查它们是否是已确认客户端工作流的硬依赖；若不是，记录理由而非复制接口。测试 HTTP capability 报告应准确反映工具清单；未来客户端预检应对必需工具/schema 缺失 fail-closed。

## 远程候选转写接口

实现者可在查看现有版本和未提交修改后选取符合命名风格的名称（建议 `transcribe_candidate`），并沿用稳定 JSON 错误/成功合同。接口语义：

- 输入：`video_uri`（一个 `nas://raw/<project>/...` 视频）、`output_uri`（`nas://projects/<configured-namespace>/<project>/...` 下候选文本文件）、可选模型/语言参数仅在 schema 和安全白名单明确时提供。客户端工作流命名空间为 `test`。
- 输出：纯文本候选稿与带时间戳 SRT 两种产物，分别使用显式逻辑 URI；成功标志、模型、检测语言、片段数、识别音频时长、耗时、必要的低置信/空结果提示；不得返回/记录物理路径或敏感异常。两项产物须先在同目录临时文件完整落盘，再以不覆盖方式发布；若第二项发布失败，回滚本任务已发布的第一项；任务仅在两项都可见后成功。文件系统不提供跨两个文件名的单次原子 rename，故不宣称物理上的跨文件原子性。
- 复用 `StorageResolver` 检查来源和目标；读取 raw 媒体、只允许 projects 当前 namespace 写候选文本；独占创建目标，不覆盖；不得支持任意本地路径或直接指定输出目录。
- 重型推理使用后台任务，提交后返回 job ID，沿用可查询状态与取消的任务机制；不得让同步 MCP 请求超时后无跟踪地继续写文件。任务完成后才按上述可回滚顺序发布纯文本与 SRT；失败/取消时清理本任务临时文件和本任务已发布文件，并返回可审计终态。selfcheck/capability 报告模型依赖和工具名。检查冷模型下载、离线缓存、CPU 内存/时长和任务取消语义。
- 候选文本不是确认字幕；工具描述、结果字段、skill 与验收输出均明确标记候选，禁止将它直接接入 assemble。
- 保持模型行为复用：当前本地 `caption` 默认 small/zh/cpu，模型缓存/离线行为需实测；远程是否固定该默认值或允许受控参数留给实现者按配置、安全和资源限制决定，并记录在矩阵。

## 候选双文件发布恢复协议

- 开发与测试 NAS 均确认支持同目录硬链接；发布器继续使用 `os.link` 的不覆盖语义。
- 每个候选目标先在目标目录以 job 专属 `.partial` 名称独占创建并写入完整内容，flush/fsync 文件数据后记录最终逻辑 URI、暂存逻辑 URI、设备号和 inode 到 job 目录的发布日志，并原子替换日志、fsync 日志文件及父目录。
- 只有目标身份已持久记录后，才将 job 专属暂存 inode 硬链接到最终目标名。最终目标已存在时发布失败，不替换目标。
- 两个目标均发布成功后，删除日志并 fsync job 目录。失败回滚和 Worker 恢复均只删除 URI 解析后身份仍与日志一致的 inode；路径已消失或身份不同则不删除。
- NAS 暂不可用、日志无效或任一条目无法核验时保留日志，供后续恢复重试；不得因恢复错误而删除未核验目标。日志只列本任务确认创建的暂存 inode，不依据目录扫描推断所有权。
- 崩溃验收覆盖暂存文件创建、日志持久化、首个最终链接创建和第二个最终链接创建后的恢复窗口；恢复需逐一核验并删除日志记录 inode 的最终名与暂存名，验证既有/替换目标不变。

## 自动化与部署验收

- 单元测试：能力清单、URI/namespace 读写守卫、无覆盖、无物理路径泄漏、空/错误媒体、ASR mock 输出、模型不可用、异常与清理、超时/并发行为。
- 协议集成测试：真实 MCP tools/list 与 JSON schema；调用受控 fixture 验证逻辑 URI 输入/候选输出；确认候选输出路径未进入 raw/output；保证现有字幕/合成工具合同不回归。
- 验收脚本：明确检查剪辑工作流矩阵要求的工具，selfcheck capability 和配置 namespace，列目录/探针，以及新的转写工具存在；在提交 assemble 之前先检查所有预检通过。常规 acceptance 不得默默写入用户 NAS；需要单独的 opt-in integration 标记或明确 fixture 项目。
- 部署前：开发测试全绿、开发环境实际模型加载/转写验证通过、部署变更范围与用户已有修改清晰、测试环境 NAS 项目级隔离和可写路径已确认、回滚旧版本的步骤明确。
- 部署后：在测试 HTTP MCP 对专用测试 fixture 项目的短片执行受控转写到唯一候选路径；校验状态、返回字段、SRT/文本可读、段数和音频时长合理、物理路径不泄漏、输出不覆盖；再跑测试环境远程协议/验收。此验证只产候选稿，不改成片、不生成确认字幕、不合成。
- 验收通过后清理专用 fixture 下本次产生的候选文本、SRT 和临时文件，保留必要审计记录；清理范围必须精确限定到本次唯一目标。
- 部署后任一验收失败时，恢复部署前测试版本并重启对应常驻服务，再验证旧版本健康；不得留下代码版本与运行进程不一致的状态。部署包括更新测试 checkout 和重启 MCP/Worker，属于本请求授权范围。

## 风险与待实现决策

- 开发 checkout 已有用户未提交改动可能涉及同文件，必须先检查、协作式合并，并避免提交用户工作。
- faster-whisper 模型可能冷下载或模型缓存未部署到测试环境；部署验收需验证，不以依赖声明代替真实运行。
- 同步工具超时后推理仍继续的风险需结合现有 `_run_heavy` 行为检查，设计候选输出的原子发布和幂等策略。
- 需检查测试环境 mount、服务用户权限和 namespace，避免在验证中写错项目或产生不可清理对象。
- 能力矩阵的持久化位置由实现者建议放在 `docs/agents/` 或设计/验收文档；需保持单一事实源，避免客户端 skill 工具清单长期漂移。

## 验收结果

所有剪辑工作流必需能力均有矩阵条目、代码/API 合同、开发测试和部署后验证；有意排除项有明确说明；开发及测试环境的远程 capability 与实际注册工具一致；候选转写可在测试环境通过逻辑 NAS URI 安全执行，且审批闸门未被改变。
